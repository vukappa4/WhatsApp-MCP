# WhatsApp MCP - design

One always-on Go daemon. It is a WhatsApp linked device (whatsmeow), owns all state in SQLite, and serves MCP to Claude Code over Streamable HTTP on 127.0.0.1. No Python, no second process, no REST API.

## Goals

- Claude reads everything the user sees in the WhatsApp app: text, captions, replies, edits, deletes, reactions, media, voice notes as text, names, phone numbers, timestamps.
- No manual steps. The daemon starts at logon and recovers on its own.
- Claude always knows how fresh the data is. Stale data is never served silently.
- Claude sends messages and files, gated by the user's intent.

## Stack

- Go, single module `github.com/vukappa4/whatsapp-mcp`, single binary (`whatsapp-mcp.exe` on Windows, `whatsapp-mcp` on macOS), `CGO_ENABLED=0`. Windows 10/11 and macOS 13+ (Apple Silicon and Intel; Go 1.27 needs macOS 13) are supported; Linux builds and runs, without `install`.
- `go.mau.fi/whatsmeow` (latest), `modernc.org/sqlite` (driver name `sqlite`).
- `github.com/modelcontextprotocol/go-sdk` v1.8.x, Streamable HTTP, `Stateless: true`, so a daemon restart never strands a Claude Code session.
- Transcription: shell out to `parakeet-cli` (whisper.cpp, model Parakeet TDT 0.6b v3, q8_0) fed by `ffmpeg -> 16 kHz mono WAV` on stdin. `whisper-cli` with `large-v3-turbo-q8_0` is the switchable fallback. Child processes run below normal priority: on Windows with `HideWindow`, `CREATE_NO_WINDOW` and `BELOW_NORMAL_PRIORITY_CLASS`, on macOS through `/usr/bin/nice -n 10`. On Windows no transcription outlives the daemon, however it ends: `run` puts itself in a job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` right after taking the profile lock, its children join the job, and Windows kills them when the daemon ends. On macOS the children share the daemon's process group, which launchd kills when the daemon it started ends; a `run` started by hand and killed with SIGKILL leaves a running transcription to its timeout.
- Windows build: a console program with an embedded manifest (see Packaging). Log to a rotated file, `debug.SetCrashOutput` to the same file.

SQLite DSN for every DB: `file:<path>?_pragma=foreign_keys(1)&_pragma=busy_timeout(10000)&_pragma=journal_mode(WAL)&_pragma=synchronous(NORMAL)&_txlock=immediate`. whatsmeow's `Upgrade` refuses to run without `foreign_keys`.

## Layout

```
cmd/whatsapp-mcp/      main: subcommands run | pair | unlink | status | stop | reingest | import-legacy | setup-transcription | install | uninstall | setup-claude | hook
cmd/whatsapp-mcp/manifest/  Windows application manifest resource, linked in cgo-free builds
internal/config/       app dir, data dir, flags, token
internal/logx/         the profile log: size-rotated file, crash output to the same file, whatsmeow logs adapted
internal/instance/     the profile lock: one process per profile (named mutex on Windows, flock on macOS)
internal/store/        schema, migrations, queries, FTS5
internal/wa/           whatsmeow client, event ingestion, connection log
internal/people/       identity merge (LID <-> phone), display names
internal/textfold/     the one name comparison (case, accents, punctuation ignored), shared by the server and the send gate
internal/media/        download, cache, media retry, transcription queue
internal/childproc/    helper processes: hidden window, low priority, ffmpeg lookup (shared by transcription and voice notes)
internal/outgoing/     send_file: path policy, kind and size limits, voice-note conversion, image metadata
internal/hooks/        Claude Code hooks gating the send tools (send-intent detection, flag files)
internal/pairpage/     pair: the QR code page served on 127.0.0.1 and opened in the browser
internal/claudecode/   setup-claude: MCP registration through the claude CLI, allow rules and hooks in settings.json
internal/mcpserver/    MCP tools, freshness header, output formatting
```

## Data dir

`<app dir>/<profile>/` with profile `prod` or `dev`. The app dir (`config.AppDir`) is `%LOCALAPPDATA%\WhatsAppMCP` on Windows and `~/Library/Application Support/WhatsAppMCP` on macOS (`$XDG_DATA_HOME/WhatsAppMCP` elsewhere); never a cache folder, which cleaners empty. Never inside a git repo.

- `session.db` - whatsmeow sqlstore (keys). Owning it means owning the account.
- `data.db` - our schema.
- `media/<chat JID>/<WhatsApp message id>_<file name or kind><ext>` - downloaded media; `<file>.transcript.json` holds its transcript.
- `logs/`, `token` (random 32-byte bearer token, created on first run).
- `config.json` (optional, written by the user): `send_file_roots` replaces the folders `whatsapp_send_file` may read from (the default folders and the scratchpad rule), `send_file_extra_roots` adds folders to them; both take absolute paths, for example `{"send_file_extra_roots": ["D:\\Progetti"]}` or `{"send_file_extra_roots": ["/Users/me/Progetti"]}`. Unknown keys and relative paths are errors, reported by the next send. It is read at every send: an edit needs no restart.

`<app dir>/tools/` is shared by all profiles: `whatsapp-mcp setup-transcription [--engine parakeet|whisper|all]` installs the models (`models/`) and, on Windows, the pinned whisper.cpp Windows release (`whisper.cpp-b5454\`), each checked against a SHA-256 pinned in code; `--source-dir` uses local copies instead of downloading, verified the same way. The release ships no macOS command-line build: on macOS the engines come from Homebrew's `whisper.cpp` formula (1.9.5 is the same commit as b5454, built with Metal on Apple Silicon), found on PATH, else in `/opt/homebrew/bin`, `/usr/local/bin` or `/opt/local/bin`, and setup-transcription checks that they are there. ffmpeg, for transcription and for voice-note conversion alike (`internal/childproc`), comes from PATH, else from `tools/ffmpeg(.exe)`, else from the package manager's install: on Windows winget's Gyan.FFmpeg (`%LOCALAPPDATA%\Microsoft\WinGet\Links\ffmpeg.exe`, then its package folders, newest first), on macOS Homebrew (`/opt/homebrew/bin`, `/usr/local/bin`) or MacPorts (`/opt/local/bin`). A daemon started by Task Scheduler or launchd can lack the user's interactive PATH.

Profiles are separate linked devices. `prod` is the default; an optional second profile such as `dev` (for testing a build) runs alongside it with its own pairing, data and port. Two processes never share one `session.db`: that causes `StreamReplaced` and Signal ratchet divergence.

## Process

- `run`: single instance via the profile lock (also taken by `pair`, `unlink`, `import-legacy`, `reingest`), plus the port bind as a second guard. The lock is the named mutex `Global\whatsapp-mcp-<profile>` on Windows and an exclusive `flock` on `<app dir>/locks/<profile>.lock` on macOS; the kernel drops either when the process ends, however it ends. The lock file is never deleted: a second process would lock a new file of the same name. Checking the lock (`status`, `stop`, `install`) takes a shared `flock` for an instant, so taking the lock retries for 80 ms before refusing. The port is bound before the WhatsApp session is opened. Ports: prod 8765, dev 8766. A refused process logs one warning saying the process holding the lock keeps running unaffected; a refused `run` (the autostart retries every minute after a failure, and on Windows every 5 minutes as watchdog) logs it at most once an hour (`logs/run-refused.mark`). `run` writes `daemon.pid` as soon as it holds the lock, before migrations, so `install` and `stop` find a daemon that is still starting. Every log line carries the writing process's `pid`, since all processes of a profile share one log file.
- `run` and `pair` share one lifecycle (`wa.Lifecycle`): `daemon_start` with mode, version and pid, a heartbeat every minute, and `daemon_stop` as a clean stop when they end.
- `stop`: POSTs `/admin/stop` with the bearer token, again every second while the daemon does not listen yet (still migrating or finishing a reingest) and holds the lock. The daemon stops accepting MCP requests, refuses new sends ("the daemon is stopping", nothing queued) and waits for a send already running to finish and be stored (up to 2 min 10 s: a send and its storage are bounded by 2 min), then disconnects, lets in-flight handlers finish, logs `daemon_stop` as a clean stop and exits. After `--timeout` (2 min 40 s, enough for that wait) `stop` kills the PID in `daemon.pid`.
- At startup `run` replays every archived event not yet ingested. `reingest` (daemon stopped) rebuilds all derived tables from `raw_events` in three passes: content (messages, history blobs, group changes, legacy rows), then the profile session's LID map and address book, then chat state, so every archive, pin, mute and read finds its chat. Media rows are kept and relinked (see Media). The transaction that empties the derived tables also sets `sync_state` `reingest_running`; the end of the rebuild clears it. A `run` that finds it (a reingest killed halfway) finishes the rebuild before serving: MCP requests wait on the bound port instead of reading half-built data. `status` shows an interrupted reingest.
- Launched at login and restarted after a failure: on Windows by Task Scheduler, with a 5-minute watchdog (no console window from Windows 11 24H2 on, see Packaging); on macOS by a launchd LaunchAgent (see Packaging).
- Connects with whatsmeow auto-reconnect. Handles `Connected`, `Disconnected`, `LoggedOut`, `StreamReplaced`, `TemporaryBan`, `ClientOutdated`, `KeepAliveTimeout`, `OfflineSyncPreview`, `OfflineSyncCompleted`, `AppStateSyncComplete`, and records each transition in `connection_log`.
- `SynchronousAck = true` with `EnableDecryptedEventBuffer = true`: WhatsApp gets the ack only after the handler returns, and the decrypted plaintext stays buffered in `session.db` until then. Every live message is written to `raw_events` in its own committed transaction before ingestion; the handler fails (no ack, redelivered from the buffer) only when that archive write fails. The raw message is archived before anything that decodes it further: a poll vote is decrypted after the archive and added to the archived payload. Ingestion errors are recorded on the raw event and retried at startup.
- Storage errors: a failed archive write (disk full, I/O error, a locked file past the busy timeout) is shown in `whatsapp_status` ("Storage: ERROR since ...", `storage_error`) and in the freshness line ("STORAGE ERROR since ...: new messages are not being saved", stale), and schedules a reconnect (`ResetConnection`) 30 s later, doubling up to 10 min while writes keep failing: WhatsApp redelivers unacked messages on a new connection, so they come back within minutes instead of whenever the connection next drops. The next successful archive write clears the error. A group change that cannot be archived is lost (WhatsApp acks notifications whatever the handler returns): the handler reports failure and runs the group name refresh, which restores the current name and description. A sent message's archive is retried (1 s, doubling up to 15 s) until the send's 2-minute deadline.
- Panics: whatsmeow recovers a panicking handler and acks the message, so the handler recovers first. A panic before the message is archived returns false (no ack, redelivered); one after it acks, since the message is safe. Ingestion (live, startup replay, `reingest`) recovers per raw event: the panic is logged with its stack and recorded on the event as a final error (a replay would panic again; `reingest` retries it), and the next events go on. A batch transaction holding a panicking event is rolled back and its events are applied one per transaction. Every transaction rolls back when its function panics, so no connection keeps the write lock. The MCP SDK runs each request in its own goroutine without a recover, so a receiving middleware recovers it: the panic is logged with its stack, a tool call answers with an error result that keeps the panic value out (it may quote message content), and the daemon keeps serving. A send that panics may have gone out, so its answer allows a retry only with the same `idempotency_key`. The media download and transcription workers recover per task the same way: the task fails with an internal error, and a waiting `whatsapp_get_media` gets it as the download or transcript error.
- `ManualHistorySyncDownload = true`: a history sync notification is archived (`history_notification`) before its message is acked. A worker downloads each blob, archives the decoded `HistorySync` proto (`history`), marks the notification done, deletes the blob from the server, then ingests it: its LID mappings and push names in short transactions like the identity sync (below), then one conversation per transaction: a failing conversation is logged and skipped, the rest lands, and the blob stays archived for `reingest`. The worker runs every 15 s and on every new notification, and only while WhatsApp is connected: nothing is tried, and no attempt counted, while disconnected, and a download cut by a lost connection is not an attempt either. A failed download is retried after 30 s, then 1, 2, 4 ... minutes, capped at 1 h (`raw_events.attempted_at` and `attempts`), for as long as WhatsApp keeps the blob: a failure becomes final only when the server answers 404 or 410 or the notification is older than 14 days. A panic while handling one blob is recorded on it and retried like a failure. `reingest` makes every notification that failed for good pending again (done ones stay done), so the daemon tries their blobs once more.
- On `Connected` the offline queue is assumed to be replaying until `OfflineSyncCompleted`; the freshness line says so instead of "synced up to".
- Sleep and resume: a clock watcher ticks every 30 s and compares each tick with the previous one on both the wall and the monotonic clock. A wall step more than 2 minutes past the tick, or the two clocks disagreeing by more than a minute, means the system slept (or the clock was changed): the daemon logs `suspended` in `connection_log` at the last tick before it (an offline gap that the next `connected` closes), shows the state `reconnecting` ("RECONNECTING after system sleep ... - results may be stale") with the offline queue unknown, and forces a reconnect (`ResetConnection`) so WhatsApp replays what was missed now instead of after a keepalive timeout.
- `EmitAppStateEventsOnFullSync = true`: a full app-state sync, and a recovery, dispatch their archive, pin, mute and mark-read mutations as events, so chats get the current state, not only later changes.
- On app-state LTHash mismatch in an incremental sync, refetch that collection with a full sync, one at a time and paced per collection: after the n-th refetch the next waits 1 min, doubling up to 1 h (a mismatch that returns after every successful full sync cannot loop); the count starts over after a day without refetches. When the full snapshot also fails the check, the collection is broken on the account side: ask the phone for a plain copy with `BuildAppStateRecoveryRequest` (sent with `SendPeerMessage`), at most once per backoff period per collection (1 h, doubling, capped at 24 h). Attempts persist in `sync_state` (`app_state_recovery:<collection>`) across restarts. whatsmeow applies the answer and emits `AppStateSyncComplete` with `Recovery` set, logged as `app_state_recovered`; the backoff stays, because the server copy is still broken. A server full sync that succeeds clears it. `BuildFatalAppStateExceptionNotification` is never sent: it makes the phone reset the collection and logs out every linked device.
- Pairing (`pair` subcommand, console): sets `RequireFullSync = true` and a generous `HistorySyncConfig` before linking, so the first sync brings as much history as the phone allows. `pair` holds the same profile lock as `run`, records the same lifecycle, then stays connected until no history notification has arrived for 2 minutes and every archived notification and blob is downloaded and ingested. Blobs that make no progress for 10 minutes (no arrival, the pending count not falling) end the wait with a warning: the daemon keeps retrying them.
- Pairing shows the QR codes on a local page it opens in the default browser (`internal/pairpage`), as WhatsApp Web does: an installer agent runs `pair` in the background, where a terminal QR would never reach the user. The page is served on `127.0.0.1` at a free port under a random path, answers only to its own `Host` (no DNS rebinding), polls the state every second and shows the current code as SVG, then "Linked as ..." while the history arrives, then done or the error. It stays up 3 s after `pair` ends so the page sees the final state. If the page cannot start or the browser cannot open, the URL is printed, or the QR goes to the terminal; `--no-browser` prints terminal QRs. A login lasts about 160 s, until the server stops issuing codes; `pair` runs 3 of them (about 8 minutes) before giving up, waiting for each finished login to disconnect before the next. `pair --phone <number>` (country code required: `+39 ...` or `0039 ...`) shows one pairing code instead, requested with whatsmeow `PairPhone` right after the first QR event, to type on that phone under Linked devices > Link with phone number instead; the QR codes keep coming meanwhile and are ignored, and the code lives one login.
- `unlink` (daemon stopped, it takes the profile lock) connects and calls whatsmeow `Logout`: the phone drops the device and the session keys are deleted. `data.db` and media stay.
- Identity sync: on `Connected`, on every `AppStateSyncComplete` (address book names arrive through app state), after every ingested history blob and in `reingest`, the account's own JIDs, whatsmeow's LID map and its address book (`whatsmeow_lid_map`, `whatsmeow_contacts`) go into `persons` and `jids`. The first sync of a large account links tens of thousands of LIDs, nearly each a merge, so it must not hold the write lock throughout: it reads what `data.db` knows in one read-only statement, keeps only the links and names that would change something, and writes those in their original order in short transactions (at most 200 steps or 50 ms each, 50 ms apart: SQLite has no queue for its write lock, and without the pause the next batch would take it again before a waiting writer polls). A live message archive or any other writer waits about one batch (longer only behind a single heavy step, such as the merge of two large DM chats). Every step is idempotent, so a sync cut short is completed by the next one. A step on a person that an earlier step of the same sync changed always runs, so with no other writer the result is that of applying every link and name in order in one transaction. A live write between batches lands as if the skipped steps ran before it and the applied ones after; readers can see a sync half applied (two persons merged, the contact name not yet set), which shows a profile name and makes the send gate ask, never pass. The next sync, at the latest, applies what a live write left behind. A trigger during a run queues one more run after it (at most one), so names from an app-state sync that completes meanwhile land at once.
- On `Connected` the daemon refreshes names: joined groups (`GetJoinedGroups`), subscribed newsletters that have a chat (`GetSubscribedNewsletters`), then up to 30 groups still without a name, most recent first, with `GetGroupInfo`. An answer about the group itself ("not in group" for a left group, "does not exist", no name) is recorded on the chat (`info_attempts`, `info_checked_at`, `info_error`) and retried after 6 h, doubling up to 30 days. Any other error (rate limit, timeout, lost connection) ends the run without recording.
- MCP SDK logs at Info level for every stateless request ("server connecting", "session initialized"); they are written at Debug.
- `run` on an unpaired profile does not connect: MCP serves the stored data. `whatsapp_status` (not paired, or logged out) and a refused send give the steps to link again, with the path of the running program, since `whatsapp-mcp` is not on PATH: `stop`, then `pair` at once in the background (the autostart restarts a stopped daemon within minutes, and pairing needs the profile lock; `unlink` first when `pair` finds the profile still paired), then `install` once `pair` has exited. They run in a shell: the WhatsApp tools are gone while the daemon is stopped. The freshness line only says `NOT PAIRED` and points to `whatsapp_status`.
- Never sends presence or read receipts. The phone keeps its notifications and unread badges.
- MCP HTTP requires `Authorization: Bearer <token>` (401 otherwise), rejects any `Origin` other than `http://127.0.0.1:<port>` or `http://localhost:<port>` (403), binds 127.0.0.1 only. Responses are plain JSON (`JSONResponse: true`).

## Packaging

- Windows: one binary, `whatsapp-mcp.exe`, console subsystem. Its manifest (`cmd/whatsapp-mcp/manifest/whatsapp-mcp.manifest`, linked through `rsrc_windows_amd64.syso` and `rsrc_windows_arm64.syso` in that package, regenerated with `go generate ./cmd/whatsapp-mcp/manifest`; main imports the package only in cgo-free builds, the production build `CGO_ENABLED=0`, because a cgo build such as `go test -race` gets a default manifest from the C linker and two manifests do not merge) sets `consoleAllocationPolicy` to `detached` (Windows 11 24H2 and later). Started from a terminal (Git Bash, PowerShell, cmd), it inherits that console like any CLI: the shell waits, sees the exit code, and pipes and redirections pass through untouched, so the hooks read JSON from stdin as given. Started without a console (Task Scheduler), Windows 11 24H2 and later create none, so `run` shows no window. Windows 10 and Windows 11 before 24H2 ignore the policy and open a console window for `run`: closing it stops the daemon until the watchdog starts it again.
- Never `-H=windowsgui`: cmd and PowerShell do not wait for a GUI-subsystem program and lose its exit code, and PowerShell gives it no stdout, so CLI output lands after the prompt or nowhere.
- `install --profile prod|dev` copies the running binary to `<app dir>/bin/` (prod) or `bin-dev/` (dev), outside every data dir. The copy goes to `<exe>.new`; the current exe, even while it runs (Windows allows renaming a running exe, not deleting it), moves to `.old`; the new one takes its name; a failure moves the old one back. Then install registers or replaces the autostart (on Windows its watchdog covers any later failure from then on), stops the profile's daemon (clean stop, kill after 2 min 40 s, then waits for the process to end), starts it through the autostart, waits (up to 3 minutes, a slow start included) until the daemon runs from the installed path, and deletes the leftovers that no longer run. The installed path is checked through the process's image: `QueryFullProcessImageName` on Windows, the executable path of `kern.procargs2` on macOS.
- The task `WhatsApp MCP (<profile>)` (registered from XML with `schtasks /Create /XML /F`): logon trigger for the current user; a time trigger repeating every 5 minutes as watchdog with `MultipleInstancesPolicy` `IgnoreNew`, so it starts the daemon only when it is not running; `InteractiveToken`, least privilege (runs only while the user is logged on, no stored password); no execution time limit; runs on battery; restart on failure every minute up to 999 times; normal priority. Restart on failure covers a start that fails; Task Scheduler does not count a daemon that crashes or is killed as a failed task, so the watchdog brings it back (273 s after a hard kill when measured). The action is the installed exe with `run --profile <profile>`, no wrapper.
- The LaunchAgent `io.github.vukappa4.whatsapp-mcp.<profile>` (`~/Library/LaunchAgents/<label>.plist`, loaded with `launchctl bootstrap gui/<uid>`): `install` and `uninstall` first stop the daemon cleanly (a clean exit is not restarted), then `bootout` and wait until launchd no longer lists the job; `install` then runs `launchctl enable` (an agent switched off in Login Items cannot be bootstrapped) and `bootstrap`. The plist sets `RunAtLoad`, so it starts at login and when installed; `KeepAlive` `{SuccessfulExit: false}`, so launchd restarts a daemon that crashes, is killed or exits with an error, and a clean exit (`stop`, or the SIGTERM of `bootout` and logout) stays stopped; `ThrottleInterval` 60 s, the least time between two starts, so a daemon that fails at start is tried once a minute as on Windows (one that ran longer restarts at once); `ExitTimeOut` 160 s after SIGTERM before SIGKILL, enough for a send in flight; `PATH` with `/opt/homebrew/bin` and `/usr/local/bin` in front of launchd's default; `ProcessType` `Interactive`, since the daemon answers Claude interactively. The program is the installed binary with `run --profile <profile>`, no wrapper. macOS ties the Files and Folders and Full Disk Access permissions to the binary's ad-hoc signature (arm64; unsigned Intel builds by path), which every build changes: after an update macOS may ask again, and a Full Disk Access entry added by hand stops applying until it is removed and added again. A file it refuses fails with EPERM, reported as a missing privacy permission.
- `stop` on an installed profile is temporary: on Windows the watchdog starts the daemon again within 5 minutes, on macOS it starts again at the next login or `install` (at once when `stop` had to kill it). A `run` started then while `reingest` or `pair` holds the profile lock is refused and tried again. `uninstall --profile X` removes the autostart first (deletes the task; on macOS stops the daemon cleanly, `bootout`, deletes the plist), then stops the daemon and deletes the installed binary; data stays. The `PreToolUse` hook is registered with `"onFailure": "block"` (see Send permissions), so a missing binary (between the two renames of an install, or after `uninstall`) blocks the send instead of letting it through; `setup-claude --remove` takes the hooks out.
- `setup-claude [--profile] [--remove]` registers the installed binary with Claude Code. The MCP server goes in through the claude CLI (`claude mcp add --scope user --transport http`, with the bearer token as an `Authorization` header), under `whatsapp` for prod and `whatsapp-<profile>` otherwise, replacing a server of that name only when `mcp add` says it already exists. The CLI and the settings file follow `CLAUDE_CONFIG_DIR` (default `~/.claude`), so it runs once per config dir. In `settings.json` it adds the allow rules for the read tools and the two hooks; hooks of an earlier registration (a command whose program is `whatsapp-mcp` or `whatsapp-mcp.exe`) are replaced, so all profiles share one pair of hooks. They run prod's installed binary whenever prod is installed, else the profile's own: uninstalling dev never breaks prod's gate. The file is parsed keeping its key order, written through its symlink target if it is one, via a temporary file; a file that is not JSON or has an unexpected shape is refused untouched. `--remove` removes the server and its allow rules; the hooks stay, pointed at the other profile's binary, while another profile is installed, and are removed otherwise. Keys left empty are dropped.
- `status` shows the autostart's state (the task's status, or the LaunchAgent's `launchctl print` state). A profile lock this user may not open (a mutex held by another user or by an elevated process seen from a normal shell, a lock file of another account) shows as running, saying it cannot be inspected from here. `stop` kills a pid from `daemon.pid` only when it can check that it is a `whatsapp-mcp` executable.

## Data model

- `persons(id, display_name, name_source, phone_e164, is_me, saved_contact, full_name, first_name, business_name, push_name, updated_at)` - the four name candidates are kept so a merge or a later name event can recompute `display_name` without losing a better source.
- `jids(jid PK, person_id, kind)` - every phone JID and LID points to one person. Learned from whatsmeow's LID map, `SenderAlt`, `RecipientAlt`, history sync, contact events and send results. A LID is one WhatsApp account, so a person holds at most one LID and two persons with different LIDs never merge. A phone number belongs to the LID that had it last: a person known only by that number merges into the LID's person (with its DM chat); a number another LID's person holds moves to the new owner without a merge (WhatsApp gave the number to someone else), noted in `identity_notes` as "number reassigned"; an older observation only records a former number. The result depends only on the observations, not on their order, so `reingest` rebuilds the same people.
- `number_links(pn, lid, seen_at)` - every observation that a LID had a number, with the time of its newest evidence (message time for `SenderAlt`/`RecipientAlt`, send time for a send result, the sync time for whatsmeow's LID map, a history blob's mappings and the account's own JIDs, which carry no time of their own). A pair seen again from a source without times changes nothing. `persons.phone_e164` is derived: the number its LID was seen with last; the person's other numbers are former ones (still found by search and old messages).
- `chats(id, jid, kind dm|group|newsletter|broadcast, person_id, name, description, archived, pinned, muted_until, unread_count, state_updated_at, archived_set_at, pinned_set_at, muted_set_at, read_set_at, info_attempts, info_checked_at, info_error, last_message_at, created_at)` - one DM chat per person, whatever JID the message used. A DM chat is created by its first stored message, never by a history conversation, legacy chat row or chat state alone; groups are stored with their name even without messages. `name` and `description` hold group, newsletter and broadcast data; DM titles come from the person.
- Chat state comes from app-state events (`Archive`, `Pin`, `Mute`, `MarkChatAsRead`, live or from a full sync or recovery) and from the account's own read receipts sent by another device (`read`, `read-self`). Each is archived in `raw_events` (`chat_state`) and applied only to a chat that exists. Archive, pin and mute apply when the action is at least as new as the one that set the flag (`*_set_at`). A read lowers `unread_count` to the incoming messages (not poll votes or system events) newer than what was read, the `MarkChatAsRead` message range or the receipt's newest message; it never raises it, so an old read replayed by a full sync cannot hide newer messages. A mark-as-unread raises it to at least 1. The first `INITIAL_BOOTSTRAP` or `FULL` history snapshot of a chat sets its unread count (the phone's own count) and the archived, pinned and muted flags no app-state action has set yet, and stamps `state_updated_at`; later snapshots, `RECENT` and on-demand chunks never touch chat state.
- `last_message_at` is the max `ts` of stored messages and never moves backwards; edits, revokes, reactions and poll votes do not bump it. `unread_count` comes from history sync, grows with live incoming messages, resets on own messages and drops with reads (above); poll votes and system events (group changes) neither raise nor reset it, as in WhatsApp. A chat's last message in `list_chats` is the newest one at or before `last_message_at`.
- `messages(id INTEGER PK, chat_id, wa_id, sender_person_id, sender_jid, from_me, ts INTEGER unix UTC, kind, text, reply_to_wa_id, reply_preview, edited_at, deleted_at, forwarded, media_id, source legacy|history|live, album_wa_id)` - unique `(chat_id, wa_id)`. `album_wa_id` links an album item to its album message. When a message arrives again, the copies merge field by field: a richer source (legacy < history < live) overwrites the fields it has, a poorer one only fills gaps, an edited text is never replaced by an unedited copy, and `edited_at`/`deleted_at` keep the strongest fact. Duplicates found when two DM chats merge use the same rule, and their media rows and reactions merge too.
- Edits apply only when the editor is the author, and only if newer than the stored `edited_at`. Revokes set `deleted_at` and keep the original text; they apply when the revoker is the author, or a group admin (`edit="8"`). A history revoke stub (`REVOKE` or `ADMIN_REVOKE`) marks the stored message deleted.
- Edits, revokes, reactions and poll votes never create chats or persons. One whose target is not stored yet (WhatsApp delivered it first, or its message is in a later history blob) waits in `pending_mutations(target_wa_id, mutation_key, source, ts, payload)` as the archived message it came in, once per mutation; when a message with that WhatsApp id is stored, its waiting mutations are applied in the same transaction, oldest first (one that still finds no target, such as another chat's message with the same id, waits again). Mutations wait at most 30 days from their own time: older ones are not kept, and `run` and `reingest` drop expired ones. A history edit of a missing message is stored under the original id and creates its chat like any stored message. Votes that could not be decrypted are dropped.
- Messages deliberately not stored are logged at Debug with a reason: `ciphertext` (history stub the phone could not decrypt either), `placeholder` (content WhatsApp hides from linked devices), `stub` (encryption notice and other stubs), `no_content` (key distribution, album header...), `duplicate_media` (HD, HEVC or motion-photo copy of a stored media message). Each history blob's summary line counts them (`dropped_<reason>=N`).
- `raw_events(id, kind, dedupe_key, received_at, payload gzip, ingested_at, attempts, error)` - every live message (info plus raw decrypted proto, plus the decrypted poll vote), history notification, decoded history blob, live group change, chat state change and legacy row, archived before ingestion.
- `identity_notes(jid, other_jid, note, ts)` - facts not applied automatically, such as a contact's number change (`oldJID`/`newJID` in history), which is not proof that two numbers are one person.
- `reactions(message_id, person_id, emoji, ts)`
- `pending_mutations` - edits, revokes, reactions and poll votes waiting for their message (above); derived, rebuilt by `reingest`.
- `media(id, mimetype, filename, size, duration, direct_path, url, media_key, file_sha256, file_enc_sha256, local_path, state, error, attempts, state_at, transcript, transcript_lang, transcript_engine, transcript_error, msg_chat_jid, msg_wa_id)` - `msg_chat_jid` and `msg_wa_id` name the message the row belongs to (its chat's JID and WhatsApp id), so a reingest relinks the row; `local_path` is relative to the media root; `state` is `pending`, `downloaded`, `failed`, `expired` or `unavailable`; `transcript` NULL means not transcribed, `''` means no speech.
- `messages_fts` - FTS5 over text, caption and transcript, tokenizer `unicode61 remove_diacritics 2`: case and accents are ignored (`perche` finds `perché`).
- `connection_log(ts, event, detail)` and `sync_state(key, value, updated_at)` (newest stored message, daemon heartbeat, offline sync state, last history sync blob, last legacy import, app state recovery per collection, send results by idempotency key for 24 h). History start per chat is `MIN(messages.ts)`, not stored.
- Schema changes are append-only migrations recorded in `schema_migrations(version, applied_at)`. A migration that rebuilds a table (SQLite cannot alter a CHECK) runs on one connection with foreign keys off, recreates the triggers that read the table, passes `PRAGMA foreign_key_check` before commit, and turns foreign keys back on (or discards the connection).

Offline gaps come from `connection_log`: a gap opens on any down event (disconnect, logout, stream replaced, ban, daemon stop) after a connected period and closes on the next `connected`. A session (run or pair) that ends without `daemon_stop` is closed when the next one starts. The previous session starts at the newest `daemon_start` or `paired` row. If the heartbeat is at or after that start, the stop goes at the later of the last heartbeat and the last event (`unclean exit: last heartbeat`). If the session never beat, its exit time is unknown and closing it at its last event would show the rest of the session as offline: the stop goes at the new start and no gap is claimed.

Display name order: saved full name, first name, business name, push name, phone number. A DM title from history (`Conversation.Name`/`DisplayName`) or a legacy chat name is a weak name: stored as the push name only while the person has no name, and replaced by any later one. WhatsApp's own account (`0@s.whatsapp.net`) is named `WhatsApp` (source `system`, rendered plain) unless the address book names it. Group names and descriptions come from history, group info and the name refresh on connect, and are refreshed on `GroupInfo` events, which also become system messages (name and description changes, members added, removed, promoted, demoted). Newsletter names come from the subscription list.

Message kinds stored: text, image, video, audio, voice, document, sticker, location, live_location, contact, poll, poll_vote, call, system. History-sync messages are unwrapped (ephemeral, view-once, documentWithCaption, edited, associatedChildMessage) exactly like live ones. Album items arrive as `associatedChildMessage` and are stored as media messages linked to the album; the album header itself holds no content. A history revoke stub without a stored message is stored as a deleted message with no text. Poll votes are stored when the client can decrypt them, as `poll_vote` replies to the poll naming the chosen options. Replies to buttons, lists and templates are text with the selected label. Messages sent through MCP are stored the moment the send succeeds, through the live path: archived in `raw_events` as a live message from the account owner, then ingested with source `live`. A sent file's media row holds the bytes that were uploaded, kept in the media folder (see Media).

`import-legacy --messages <messages.db> --session <whatsapp.db>` imports the old bridge's data read-only and idempotently: the session's LID map and address book first, then chats and messages. The legacy `sender` column is only a JID user part; it resolves to a known LID, then a known phone number, then a phone number if it parses as one, else a LID.

## Media

- Downloads use whatsmeow's `Download` with the stored direct path (else the path of the URL, query string kept: it carries the CDN tokens), media key, hashes and the media type of the kind (stickers are images). The file streams to `<file>.part` (`DownloadToFile`, never whole in memory), is checked against its SHA-256, then renamed. Three download workers; on-demand requests go before background work.
- Sent files: once a file send is stored, the bytes it uploaded (for a voice note the converted Opus audio, not the source file) are written to the message's media path, through `<file>.part` and a rename, and the row is `downloaded`. The row is held in the download queue meanwhile (a queued download of it is taken over, a running one finished first), so a sweep never fetches the file back while it is written. `whatsapp_get_media` serves them without a download, offline too, whatever happens to the original. The archived event carries no path: the bytes match the message's SHA-256, so a row rebuilt by a `reingest` adopts the file like a downloaded one. A failed write never fails or repeats the send: it is logged and the row stays `pending`, downloaded like any other.
- New live media under 50 MB is queued right after its message is committed. History media is downloaded on demand. Every 10 minutes and whenever WhatsApp connects, a sweep queues live media of the last 14 days still pending, or failed fewer than 3 times.
- On 403, 404 or 410 (or no direct path), or a file at the stored path that fails the message's hashes, an on-demand download sends a media retry receipt (incoming DMs use the sender's JID as chat, groups name the participant), waits up to 60 s for `MediaRetry`, and downloads from the new direct path. The phone is asked at most twice per file in 24 h (`media.reupload_requests`, `reupload_window_at`, so restarts do not reset it); past that the request fails as `expired` with the time it may ask again. A waiting download is keyed by chat, sender (in groups) and WhatsApp id; an answer goes to the download with the same key, else to the only one waiting for that id, else nowhere; the new path replaces the stored one only once it delivered the file. A re-upload whose hashes differ (the phone re-encoded it) is accepted when its MAC verifies with the message's media key (checked in memory, up to 256 MB). Background downloads never ask the phone: a 404 there is recorded as `expired`. An on-demand request that joins a running background download asks again on demand if that download did not get the file.
- Old history media (a month and more): the phone often answers SUCCESS with a re-upload that is a well-formed encrypted file of the original size but fails the MAC, the padding and the plaintext SHA-256 under the media key with every media type, with or without the `hash` query parameter; the answer carries no `messageSecret`. The phone encrypted it with a key it does not send, so no client can decrypt it (mautrix-whatsapp and Baileys download re-uploads with the original key too). Such media is `failed`, not `unavailable`: a later request may get a good copy.
- States: `pending` (not tried, or not connected: nothing is recorded while offline), `downloaded`, `failed` (any other error, such as no media key yet, which a later copy of the message may bring, or a re-upload under a key the phone does not share; the next request retries), `expired` (gone from the servers, the phone did not answer; the next request retries), `unavailable` (final: the phone says the file is gone, `ErrMediaNotAvailableOnPhone` or `NOT_FOUND`; never retried).
- Paths: chat JID and WhatsApp id keep only letters, digits and `@._-`; file names lose separators, reserved and control characters and are capped at 80 characters, and cut further so the whole file name with `.transcript.json` stays within 255 bytes (the macOS and Linux limit), with the chat JID and message id cut to 64 bytes; a file found under the uncapped name (possible on Windows, which counts UTF-16 units) is adopted there; the extension comes from a fixed mimetype table in code (never the system registry, which maps `audio/x-mpegurl` to `.m3u`), or from the sender's file name when it is on a short safe list and agrees with the mimetype (never for voice notes and audio); anything else is `.bin`; every stored path is resolved under the media root and refused if it leaves it; a `downloaded` row whose path is refused or whose file is gone is `pending` again once a download or a transcription reaches it, and downloads like one never fetched. `reingest` keeps the media table: a rebuilt message takes the row with its WhatsApp id that no message uses (the same chat's first), keeping its state, file, re-uploaded path, attempts and transcript; the message's fields only fill the row's gaps. Rows no message took are deleted at the end (their files stay). A media row lost anyway is rebuilt from the file on disk: JIDs and WhatsApp ids survive a reingest, so a file already there (same SHA-256) and its transcript sidecar are adopted instead of downloading and transcribing again.
- Voice notes and audio are transcribed one at a time right after download (and by the sweep), on-demand requests first. `run --transcriber parakeet|whisper|off` picks the engine (default parakeet). Threads: half the cores, at most 8. Timeout: 2 minutes plus twice the audio length, at most 30 minutes. parakeet-cli prints the text on stdout and reports no language; whisper-cli runs `-l auto -oj` into a temp file, because on Windows it writes stdin results to the console instead of stdout. Before ffmpeg runs, the first bytes are sniffed: a voice note must be Ogg, other audio Ogg, MP3, MP4/M4A, WAV, AAC (ADTS), AMR or WebM/Matroska; anything else (a playlist, concat list, SDP) is not transcribed and says so in `transcript_error`. ffmpeg then runs with that demuxer forced (`-f`), `-protocol_whitelist file,pipe` and the input as `file:<path>`, so no file a sender controls makes it open a URL. A failure is stored in `transcript_error`: the background queue skips it, an on-demand request retries. Transcripts land in FTS through the `media_fts_transcript` trigger.
- Measured on a Windows PC (16 threads, 8 used), Italian voice notes of 8, 71 and 145 s: parakeet q8_0 2.4, 13.7 and 31 s; whisper turbo q8_0 34, 75 and 130 s. Parakeet q8_0 matches f16 within about 2% of words at half the size.

## MCP surface

Server instructions under 2,048 characters cover purpose, identity model, freshness, and the untrusted-content rule.

Results are text only (plus the inline picture of `whatsapp_get_media`): no tool declares an `outputSchema` and no result carries `structuredContent`. A client may show the model only `structuredContent` when a result has it (Claude Code does), which would hide the transcript, the people and the ids. The model is the only consumer, so the text carries everything: the freshness line, every `c_N`/`p_N`/`m_N` id, cursors, counts and status fields. Tools register through `addTool`, whose handlers return no structured value; `TestToolsAreTextOnly` calls every tool and fails on an output schema or `structuredContent`.

Every read result starts with a freshness line:
`[whatsapp: connected since 08:02 | synced up to 10:41 | gap 11 Oct 22:00 - 23:10 overlaps this range]`
When disconnected: `[whatsapp: DISCONNECTED since 09:12 (logged_out) - results may be stale]`. After a system sleep, until WhatsApp connects again: `[whatsapp: RECONNECTING after system sleep since 09:12 | data up to 01:40 | gap ... - results may be stale]`.

All times shown in Europe/Rome with the offset; the freshness line uses short Europe/Rome times as in the example. Inputs accept ISO 8601 with any offset, written `+02:00`, `+0200` or `+02`; without one, a date or date-time is Europe/Rome, and a time alone (`09:00`, `9:05`, `09:00:30`) is that time today in Europe/Rome.

Read tools take `response_format: concise|detailed`. Lists page with opaque cursors bound to the tool that issued them. `whatsapp_read_chat` returns 30 messages by default and at most 100; concise mode cuts bodies at 800 characters, detailed mode at 4,000 characters (bodies and transcripts) when more than one message is asked for, each with a marker naming the call that shows the full text (`limit=1`, or `whatsapp_get_media` for a transcript). One answer stays under about 20k tokens (70,000 characters): messages past that are left out, the oldest when reading back from the newest and the newest when reading forward or around a message, the answer says how many, and the cursors reach them. `whatsapp_status` lists the newest 10 offline gaps and how many are recorded.

Sender-written text (bodies, captions, transcripts, group names and descriptions, file names, local paths whose file name a sender chose, and error messages that can quote them) is sanitized (invisible and bidi characters stripped) and wrapped in `<untrusted_whatsapp nonce=X>...</untrusted_whatsapp nonce=X>` with a random nonce per response (a send's group name too). The send tools wrap the sent file's name and any file error, since a file from the media folder carries a sender's name. Metadata stays outside the wrapper. The server instructions also call files Claude opens from `whatsapp_get_media` paths (documents, images, audio) untrusted content.

Names: address-book names render plain. Profile (push or business) names are chosen by the person, so they render like WhatsApp shows strangers, `~Name`: control, invisible and bidi characters, newlines and `<`/`>` removed, spaces collapsed, capped at 40 characters, never wrapped.

People are shown as `Marco Rossi (+39 333 123 4567)` or `~Marco (+39 333 123 4567)`. IDs are short: `p_17` persons, `c_42` chats, `m_8812` messages.

| Tool | Purpose | Annotations |
|---|---|---|
| `whatsapp_status` | Connection, account, last event, offline gaps, history coverage, storage errors, a temporary ban, and the phone's last activity: a message written or a read sent on the primary phone (device 0) or a history sync it sent (`sync_state` `phone_seen_at`, or the newest history blob); from 12 days without it the status and every freshness line warn ("PHONE OFFLINE N days"), because WhatsApp unlinks the device at 14 | read-only |
| `whatsapp_search_people` | Find people by part of a name, phone in any format, p_N id or LID; ranked list with phones, name and its source, DM and groups they wrote in, last interaction | read-only |
| `whatsapp_list_chats` | Chats by recency with filters (unread, dm, group, query), cursor | read-only |
| `whatsapp_read_chat` | Transcript of one chat (by chat, person, phone or exact name), time bounds, `around` a message, cursor, concise/detailed | read-only |
| `whatsapp_search_messages` | FTS5 search with filters from, in_chat, after, before, has_media, from_me; sort relevance or newest; 0-3 context messages per hit | read-only |
| `whatsapp_get_media` | `message` m_N, `mode` auto, transcript or path. Downloads if needed (waits up to 20 s, then says when to call again); returns metadata, local path, the wrapped transcript of voice and audio (waits up to 40 s), and images under 1 MB as image content in auto mode, only when their bytes are JPEG, PNG, GIF or WebP (the block's type is the sniffed one, never the sender's mimetype); documents and videos only as a path | read-only, open-world (downloads, may ask the phone to re-upload), not idempotent |
| `whatsapp_send_message` | Text to a person, phone or chat, optional reply; echoes resolved recipient | not read-only, not destructive, open-world |
| `whatsapp_send_file` | Image, video, document, or voice note (converted to Opus) from a local path | not read-only, not destructive, open-world |
| `whatsapp_request_history` | Ask the phone for older messages of one chat | not read-only, not destructive, open-world |

No tool sets `requiresUserInteraction`: a send the user asked for runs without a prompt. The hooks below decide when to ask.

Media in transcripts: `[voice 0:42 · transcript]` in concise mode marks a stored transcript; detailed mode adds size, mimetype and state and shows the transcript text, wrapped. Search hits always show the transcript (or its excerpt), since the match may be in it. In `whatsapp_get_media` the local path (its file name part comes from the sender) and download or transcription errors (they can quote it) are wrapped as untrusted; a mimetype shows only when it has the shape of a media type. `whatsapp_status` reports media counts per state, the download queue, and whether transcription is ready (with the ffmpeg it runs) or what is missing.

Errors are tool results with `isError: true` and a concrete next step (for example the list of candidates for an ambiguous name).

People search: names match case- and accent-insensitively on any part of the full, first, business, push or display name, and on the number. Ranking: exact id, JID or LID; whole phone number; a name equal to the query; a name starting with it; every query word starting a name word; a name containing it; part of the number; every word somewhere. Ties go to saved contacts, then the most recent interaction. A phone matches in any format (`+39 333 123 4567`, `393331234567`, `3331234567`, `0039...`); a number without `+` or `00` and at most 10 digits is Italian. A bare long number is also tried as a LID. "Groups" are the groups where the person wrote: membership is not stored. A name filter elsewhere (`from`) resolves only when one person ranks strictly first with at least a prefix match; otherwise the error lists the candidates.

Message search query syntax: plain words AND-ed, `"quoted phrase"`, `word*` prefix. Every term becomes a double-quoted FTS5 string of letters and digits only, so FTS operators, column filters, parentheses and stray quotes in user input are plain text and never a syntax error; input with no letter or digit is an error naming that. Without a query the filters list messages newest first. Relevance pages by offset, newest by a `(ts, id)` keyset. Concise mode cuts a hit to the FTS snippet around the match (texts over 300 characters) and context messages to 160 characters, each with a pointer to the full text; default page 20 hits, 10 with context. Default responses stay under 5,000 tokens; `TestRealData` measures them.

## Sending

- Sends need the running daemon, paired and connected. Otherwise the tool fails at once with the state and the fix (pair again, wait for `connected`): nothing is queued, so a send never fires later, out of context.
- Recipient (`to`): a `c_N` chat (DM or group), a `p_N` person, a phone number in any format (same parsing as people search), or a name. A name must equal one person's full, first, business, push or display name, or one group's name, case and accents ignored; prefixes never count. When a person matches only through a name they chose themselves (push or business name), saved contacts whose name starts with the query are candidates too: a stranger calling themselves "Giulia" never wins over the saved "Giulia Verdi". Several candidates return the list with phones; none returns the closest people. Newsletters and broadcast lists are refused.
- A DM goes to the person's LID (the account) whenever one is known: a stored number can be out of date, or WhatsApp may have given it to someone else. Only a person with no known LID gets the send at their phone JID. A person holding two LIDs (data merged before a LID was one account) is refused until a `reingest` splits them. A send result naming another person's LID is never merged into the recipient. A phone number without a stored DM chat is checked with `IsOnWhatsApp` first: no account is an error, and the send goes to the number WhatsApp returns.
- A recipient with no stored message in any chat (no DM message, never wrote in a group) gets the send, and the result says "first message to this number": messaging strangers is what WhatsApp bans for. The send tool descriptions forbid bulk and unsolicited sends.
- `reply_to=m_N` must be a message of the recipient's chat. The reply carries `ContextInfo` with the quoted message's WhatsApp id, its author as stored (phone JID or LID; the account's phone JID for my messages without one) as participant, and a quoted message rebuilt from the stored kind and text.
- The result gives the stored `m_N`, the chat, the recipient as `Name (+39 ...)` or the group name, and the server timestamp. A send that succeeded but failed to store says so and must not be repeated.
- Send and storage run on their own 2-minute deadline, detached from the MCP request: once a message is on the wire, a cancelled request does not abandon it. A send WhatsApp did not confirm (timeout or cancel) says the message may or may not have arrived.
- `idempotency_key`: every send carries a WhatsApp message id chosen before it (`GenerateMessageID`, passed as `SendRequestExtra.ID`). Before the send, an "unconfirmed" record with that id is written under the key in `sync_state`; the result replaces it, and a send WhatsApp refused outright removes it. Records live 24 h. The same key with the same arguments returns the stored result without sending; with different arguments it is an error. An unconfirmed record whose message id turns up stored as a message from this account (a crash between the send and the result, or a later history sync from the phone) is resolved as sent, with its `m_N`, both when its key is used again and by a pass over all records at daemon start; otherwise the answer says to check `whatsapp_read_chat`. Sends run one at a time, so the check is exact.
- `whatsapp_send_file` kinds: `auto` sends JPEG and PNG (by content, not extension) as photos, MP4 as video, everything else as a document. `image` and `video` refuse other formats. `voice_note` converts audio to Ogg Opus 16 kHz mono: the checked file is copied from its open handle to a private temp file, its container is sniffed (Ogg, WAV, MP4/M4A/MOV, AMR, Matroska/WebM, FLAC, MP3, AAC; anything else is refused) and ffmpeg runs on the copy with that demuxer forced and `-protocol_whitelist file,pipe` (child process with a hidden window), so a playlist never reaches it; with PTT, duration and a 64-bar waveform measured on the converted audio; voice notes take no caption. Photos carry width, height and a 72 px JPEG thumbnail.
- Size limits: 16 MB for photos, videos and voice notes (WhatsApp's media limit), 100 MB for documents (the upload holds the file in memory), 200 MB for the audio a voice note is converted from.
- Path policy (`internal/outgoing`): an allowlist, then a denylist. A file must be inside an allowed folder: by default the user's `Desktop`, `Documents`, `Downloads`, `Pictures`, `Videos` (`Movies` on macOS) and `Music` (on Windows also wherever its known folders point), every cloud drive folder (`~/OneDrive*`; on macOS every `~/Library/CloudStorage/<drive>` and iCloud Drive, `~/Library/Mobile Documents/com~apple~CloudDocs`), the profile's `media` folder, and in Claude Code's temp folders (`%TEMP%\claude` on Windows; on macOS `claude` and `claude-<uid>` in `$TMPDIR` and in the user temp dir from `getconf DARWIN_USER_TEMP_DIR`, since launchd may give the daemon no `TMPDIR`, and `/tmp/claude-<uid>`) only paths through a `scratchpad` folder (where Claude sessions write the files they generate; the rest holds session task transcripts); `config.json` changes the list (see Data dir). The path must be absolute (on Windows on a local drive letter), to a readable regular file with one hard link. On macOS and Linux it is opened with `O_NONBLOCK`, so a named pipe is refused instead of blocking the open. The name rules run on the path as given; then the file is opened once, and the OS's final path for that handle must pass them again and lie inside an allowed folder (as written or resolved), case-insensitively (as default APFS and NTFS compare). The final path comes from the handle itself: `GetFinalPathNameByHandle` on Windows (symlinks, junctions such as `C:\Documents and Settings`, mount points and 8.3 names resolved), `fcntl(F_GETPATH)` on macOS, `/proc/self/fd` on Linux, so a symlink swapped after the open cannot redirect the check. Everything uploaded is read from that same handle, so the file checked is the file sent. Refused even inside allowed folders: UNC and device paths (`\\server\...`, `\\?\`, `\??\`, `/\...`, `//server`), on Windows alternate data streams (`file:stream`; elsewhere `:` is an ordinary character), files with more than one hard link (a second name could hide a secret), anything under the app dir except `<profile>/media/` (sessions, data, tokens, logs, hook flags, lock files), the profile data dir outside its `media` folder, `~/.config`, every `~/.claude*`, on macOS all of `~/Library` except its cloud drive folders and the media folders (app data, mail, messages, keychains, cookies, every browser profile), on Windows the browser profile dirs (Chrome, Edge, Brave, Chromium, Vivaldi, Firefox, Opera, Thunderbird), any path through a `.git`, `.ssh`, `.aws`, `.azure`, `.docker`, `.kube` or `.gnupg` folder, and files named `*.pem`, `*.key`, `id_*`, `.env*`, `token`, `session.db*`, `whatsapp.db*` (the legacy bridge session), `.git-credentials`, `.netrc`, `_netrc`, `.npmrc`, `.pypirc`, `*.kdbx`, `*.pfx`, `*.p12`, `*.ppk`, `*.ovpn`, and any database (`*.db`, `*.db-*`, `*.sqlite`, `*.sqlite3` and their journals).
- `whatsapp_request_history(chat, count=50)`: anchors whatsmeow's `BuildHistorySyncRequest` at the chat's oldest stored message (system messages excluded) and sends it with `SendPeerMessage`. The phone answers asynchronously, only while online, with a history sync notification of type `ON_DEMAND`; it goes through the normal notification archive, blob download and ingestion, and never touches chat state. The result says to check later with `whatsapp_read_chat`. Requests go to the phone, so they are rationed: one per chat every 10 minutes and 20 a day (Europe/Rome day), counted in `sync_state` (`history_request:<chat id>`, `history_requests_day`); past that the tool says when to ask again.
- Temporary ban: `TemporaryBan` is stored with its end (`sync_state` `temporary_ban`; 24 h when WhatsApp gives no duration) and survives restarts. Until it ends every send and history request is refused ("temporarily banned ... until"), whatever the connection state, and `whatsapp_status` shows it.

## Send permissions

- Read tools: allowed in Claude Code permissions, never prompt.
- Send tools and `whatsapp_request_history`: two hooks, both subcommands of the daemon binary (`whatsapp-mcp hook user-prompt`, `whatsapp-mcp hook pre-tool`), registered by `setup-claude` together with the allow rules for the read tools. A send is never triggered by content Claude read in a message.
- `UserPromptSubmit` (`hook user-prompt`): reads `session_id` and `prompt` from stdin. When the user's own prompt asks to send, it writes the flag `<app dir>/hooks/<session_id>`: JSON with the time and the prompt folded to words (lowercase, accents stripped, punctuation dropped, at most 20,000 words). The hooks dir and every flag are readable by the current user only (written to a `.tmp` file, restricted, then renamed): a protected DACL on Windows, modes 0700 and 0600 on macOS. Otherwise it deletes the flag. Any failure (unparseable JSON, no `session_id`, no hooks dir, a failed write) deletes the session's flag when the session id can be read, even with a regular expression from broken input: an old intent never outlives a prompt. The flag lasts one turn (the next prompt rewrites or clears it) and at most 2 h. It always exits 0 and prints nothing: Claude Code adds a `UserPromptSubmit` hook's stdout to Claude's context. Session ids that are not plain file names are hashed; expired flags are pruned.
- `PreToolUse` (`hook pre-tool`, matcher `mcp__[A-Za-z0-9_-]*[Ww][Hh][Aa][Tt][Ss][Aa][Pp][Pp][A-Za-z0-9_-]*__(whatsapp_send_.*|whatsapp_request_history|send_message|send_file|send_audio_message)`): gates every server whose name contains `whatsapp` in any case (prod, a dev registration, the legacy bridge's send tools), whatever name it is registered under. It reads `session_id`, `tool_name`, `tool_input`. The flag is necessary, not sufficient: the call passes silently (prints nothing, exits 0, so Claude Code's normal permission flow decides) only when the flag is fresh and the recipient is recognizable in the stored prompt, and for a file send the file is mentioned too. Otherwise it prints `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"ask","permissionDecisionReason":"WhatsApp: <why>. Confirm this send to <recipient>."}}` (history requests: "Confirm this history request for <chat>."), the reason being no send intent in the last message, a recipient it does not name, no file mentioned, or a recipient that cannot be looked up.
  - Recipient: `to` (legacy tools: `recipient`; history: `chat`) is resolved in `<profile>/data.db` opened read-only with a 1 s busy timeout; the profile is `dev` when the MCP server name contains `dev`, else `prod`. `p_N` gives the person's address-book names (full, first) and phone numbers (phone JIDs included); the names the person chose (push, business, a display name taken from them) count only for a saved contact or someone the user has written to, since a stranger can call themselves "Marco". `c_N` gives a DM's person, or a group's name when the user has written in that group (any member can rename a group). A phone number (or a legacy JID) gives the person or group holding it now, as the send tools find it: a former number WhatsApp gave to another account names that account, never its former owner. The label shows the person's current number. A send's `to` name is resolved as the send tools resolve it, through the same `textfold.Fold` (a person's or a group's name equal to it with case, accents, emoji and punctuation ignored), and gives those candidates' trusted names; a name nobody has is a lookup error, so the gate asks. Matching names any other way would let the server find a stranger the gate never saw. For the same reason the send tools match a group by name only for a plain name: a `to` with `@` names a person by JID, and one starting with `c_` or `p_` that is not an id is refused. A history request's `chat` name goes through the same lookup, while `whatsapp_request_history` itself finds chats by exact name (ASCII case ignored); a mismatch there can only ask the phone for history, never send. An untrusted recipient is still recognizable by its number or its id. It is recognizable when the prompt holds any word of at least 3 letters of one of those names (case and accents ignored; name stopwords such as `del`, `della`, `van` never count), the last 6 digits of one of its phone numbers (digits of adjacent number words joined, so `+39 333 123 4567` counts), or the id itself (`c_42`). The reason names the recipient as `Name (+39...)`, `~Name` for a name the person chose, or `group <name>`, stripped of control and bidi characters and capped at 80 characters.
  - Nicknames are unknown to the check: a contact saved as "Lorenzo" and called "Enzo" in the prompt costs one confirmation prompt.
  - File: `whatsapp_send_file` (legacy `send_file`, `send_audio_message`) also needs the prompt to mention a file: a file word (`file`, `pdf`, `documento`, `allegato`, `foto`, `immagine`, `audio`, `vocale`, `video`, `presentazione`, `slide` and English equivalents), the file's extension, or a word of at least 4 letters of its name (`manda il business case` matches `Business_Case_v2.pdf`).
  - It fails closed and on time: unreadable input, no hooks dir, a missing, corrupt or expired flag, a lookup error or a lookup still running after 4 s all ask. It never touches the network. When it cannot even print its decision it exits 2, which Claude Code treats as a block.
- `setup-claude` registers both hooks in exec form (`command` is the installed exe, `args` its arguments): Claude Code spawns the binary directly, with no shell. The installed binary's path holds a space on macOS (`Application Support`), which exec form passes untouched. Without `args` Claude Code would run the command through a shell (on Windows Git Bash, or PowerShell when Git Bash is missing), where a shell suffix such as `|| exit 2` is not reliable (Windows PowerShell 5.1 does not parse `||`); never register the hooks in shell form. The `PreToolUse` hook sets `"onFailure": "block"` (Claude Code 2.1.295 and later), so a gate that cannot start (missing binary between the two renames of an install, after `uninstall`), exits with another code, prints invalid output or times out blocks the send; without it Claude Code lets the call through. The `UserPromptSubmit` hook keeps the default (`continue`): a failure there must not reject the user's prompts. The previous turn's flag it leaves behind authorizes nothing: `hook pre-tool` reads the end of the session transcript (`transcript_path`, the last 8 MB) and asks when its newest typed prompt (a `user` entry with text, not a tool result, meta entry, subagent entry or `!` shell command) is more than 5 s newer than the flag and has other words. A transcript that cannot be read, or that has not recorded the current prompt yet, leaves the flag as it is. Both hooks have a 10 s timeout. The matcher spells `whatsapp` in both cases letter by letter (`[Ww][Hh]...`): matchers are case-sensitive regular expressions, and a server registered as `WhatsApp` must be gated too.
- The hooks read stdin and write stdout exactly as Claude Code passes them (the binary is a console program, see Packaging). A UTF-8 byte order mark before the JSON is skipped: Windows PowerShell 5.1 adds one when it pipes text with `$OutputEncoding` set to UTF-8.
- Send intent (`hooks.SendIntent`), case- and accent-insensitive, per sentence: Italian and English send verbs in imperative or infinitive form, with clitics (`invia`, `inviare`, `invialo`, `manda`, `mandagli`, `inoltra`, `rispondigli`, `scrivigli`, `digli`, `glielo mandi`, `send`, `forward`, `reply`); `rispondi`, `scrivi`, `reply`, `write`, `message`, `text`, `tell` only with a recipient right after (`rispondi a Marco`, `scrivi un messaggio a Paola`, `message him`, `text Giulia`), and not when that "recipient" is a question (`rispondi alla domanda`). Not intent: any negated send verb anywhere in the prompt (`non mandarlo`, `senza inviare`, `prima di inviare`, `don't send`, `no need to reply`) cancels the prompt; any `bozza` or `draft`; an infinitive after `da`, `per`, `di`, `a`, `to` (`un testo da inviare`, `aiutami a rispondere`); questions, unless they open with a request modal (`puoi`, `potresti`, `can`, `could`...) or `glielo`; past participles (`cosa mi ha mandato Marco?`); forms addressed to the user (`mandami`, `send me`); `mandare in produzione`, `reply in English`, `look forward`. Limits: it reads words, not meaning. Any channel counts (`manda la mail a Marco`); an advice request without `?` (`cosa devo rispondere a Marco`) counts; text pasted into the prompt counts like the user's words. Requests without these forms (`lo mandi tu a Marco?`, `fagli sapere`, `I want to send...`) are missed and get a prompt. A miss costs one confirmation; a false hit leaves the decision to the normal permission flow. `internal/hooks/hooks_test.go` holds the accuracy table and pins the known limits.
- Hook input and output follow the Claude Code hooks reference (https://code.claude.com/docs/en/hooks): common input fields `session_id`, `transcript_path`, `cwd`, `permission_mode`, `hook_event_name`; `UserPromptSubmit` adds `prompt`, and its plain stdout on exit 0 is added to Claude's context; `PreToolUse` adds `tool_name`, `tool_input`, `tool_use_id`, and decides through `hookSpecificOutput.permissionDecision` (`allow`, `deny`, `ask`, `defer`) with `permissionDecisionReason`, shown to the user for `ask`. "Exit code 0 with no output means the hook has no decision to report, so the tool call continues through the normal permission flow." A hook's `ask` forces a prompt even in auto mode. MCP tools are named `mcp__<server>__<tool>` and matchers are regular expressions.
